# Phase 5H: technical-review conclusions for the Windows Toolchain 1.1 release

These are the project's **technical-review conclusions** for the Windows x64 Toolchain 1.1 (the Nexys A7 support and the DE10-Lite support), reached from the actual Windows files, the Phase 4C/5B Windows compliance inventory (`toolchains/compliance/toolchain-1.0.json`, target `win32-x64`) and the decisions already made for the macOS Toolchain 1.1 (`docs/phase5e-compliance-conclusions.md`). **They are not legal advice and no attorney has approved them.** A macOS conclusion is reused only where the exact Windows component, version and source are the same; where they differ, this file says so.

Nothing macOS-related was changed: the macOS 1.1 archives, source packages, `toolchain-1.1.json`, notices and pins are untouched; every Windows record is a new file.

## 1. What is in the Windows Toolchain 1.1

| | Toolchain 1.0 (Windows, kept as a record) | Toolchain 1.1 (Windows) |
|---|---|---|
| Nexys A7 support archive | `nexysvhdl-toolchain-1.0-win32-x64.tar.gz`, tree `57f0f0da…820b`, 21,208 files | `nexysvhdl-toolchain-1.1-win32-x64.tar.gz`, tree `4e584b73…a9d`, 21,145 files |
| DE10-Lite support archive | `mixfpga-de10-lite-support-1.0-windows-x64.tar.gz` (internal validation payload) | `mixfpga-de10-lite-support-1.1-windows-x64.tar.gz` |

The same official upstream archives with the same pins (GHDL 6.0.0 mcode UCRT64 zip; Apio 1.6.0 bundle; Apio definitions 2026.09.17; OSS CAD Suite 2026.09.15; Verible 2026.09.20; openXC7 2026.09.24 and its xc7a100t chip database). The exact difference to 1.0, byte by byte (`scripts` diff of the two trees): **144 files removed, 81 added (licence texts), 6 modified** (the notices, the manifest, the two GHDL library indexes, the two placeholder notes, which name the version).

Removed, each proved unused on Windows (not merely removed because macOS removed it):

* **VHDL-87/93 IEEE libraries, VITAL-95, VITAL-2000, UPF (30 files, GHDL `lib/ghdl`)**: MIX-FPGA runs GHDL with `--std=08` and nothing else (`core/vhdl/ghdl/ghdl-provider.ts`, the same provider on both systems); the 2008/2019 library indexes are regenerated by GHDL itself (`scripts/toolchain/ghdl-prune.mjs --check` reproduces them; every kept source keeps the upstream analysis timestamp: 29/29 and 24/24 entries identical). Checked on the pruned Windows tree: GHDL analyses, elaborates and runs a design with `--std=08` (`tests/windows-install/layout.test.ts`, "real Toolchain 1.1 tools").
* **The 111 openFPGALoader bridge bitstreams (`share/openFPGALoader/spiOverJtag_*`, `bpiOverJtag_*`)**: they have no recorded provenance and serve only openFPGALoader's SPI-flash path. On Windows nothing programs a board with openFPGALoader: the Nexys A7 is programmed with Digilent `djtgcfg` (SRAM) and the DE10-Lite with `quartus_pgm`; no file under `platform/windows` or `core` starts openFPGALoader (the Windows installer tests also forbid it), and the Phase 4C process watcher never saw it run.
* **`include/ghdl/vpi_user.h`, `synth_gates.h`, `synth.h`**: two headers without a licence statement, plus the header that includes one of them; they are needed only to compile a GHDL plugin.

Added: the licence texts of the bundled native libraries (60 groups, `licenses/compliance/`, collected in Phase 5B from the RPM headers and source packages of Fedora's MinGW packages, the static libraries and the Python runtime), and the corrected notices. The DE10-Lite archive additionally ships the three texts the Toolchain 1.0 notices marked MISSING (libffi, termcap, libwinpthread).

## 2. GNU Readline on Windows (L3). Technically resolved

The footprint was established from the import tables of **every file that is a PE image, whatever its extension** (571 images in the Nexys tree: 379 `.dll`, 152 `.exe`, 21 `.pyd`, 8 `.tgt`, 7 `.vpi`, 4 `.so`; `scripts/compliance/readline-footprint.mjs`, result in `toolchains/compliance/windows-1.1-readline-footprint.json`):

| Importer | Imports | Notes |
|---|---|---|
| `bin/yosys.exe` (ISC) | `libreadline8.dll` | also in the DE10-Lite archive (`yosys/bin`) |
| `bin/vvp.exe` (Icarus Verilog runtime, GPL-2.0-or-later) | `libreadline8.dll` | Nexys archive only; MIX-FPGA does not run it |
| `lib/libreadline8.dll` (GNU Readline 8.2, GPL-3.0-or-later) | `libtermcap-0.dll` | Fedora `mingw64-readline 8.2-3.fc39` |
| `lib/libtermcap-0.dll` (GNU termcap 1.3.1, **GPL-2.0-or-later**) | none | Fedora `mingw64-termcap 1.3.1-34.fc39` |
| `lib/libtextstyle-0.dll` (gettext) and `lib/libgettextsrc-0-22.dll` | `libtermcap-0.dll` / `libtextstyle-0.dll` | gettext tools, not Readline |

Not importers: `yosys-abc.exe`, `yosys-filterlib.exe`, `iverilog.exe`, `ivl.exe`, the `.vpi` modules, every `.pyd`; **the Python 3.11.6 of the package has no `readline` extension module on Windows** (the macOS Python conclusion does not apply). `libhistory8.dll` ships beside Readline and nothing imports it.

What is the same as macOS: Yosys is the same commit (`66306a8c`, `-dirty` from the same recipe `ac8c7dba`, with the same `abc`/`cxxopts` submodules); Icarus Verilog is the same pinned source (`6767a079`, GPL-2.0-or-later in every Icarus-authored file's header). What is different: Readline here is Fedora's `mingw64-readline` 8.2-3.fc39 (not MacPorts), termcap is a separate GPL-2.0-or-later library (macOS has ncurses/X11), and the Icarus version string carries another local-revert hash (`s20251012-140-gf5a178d47-dirty`, macOS `g5c6cdec6a`: the recipe makes a new local commit at build time).

Treatment, following Phase 5E: each program that loads Readline (`yosys.exe`, `vvp.exe`) is distributed with Readline and termcap under GPL version 3 (GPL-2.0-or-later and the ISC licence combine under GPLv3), with the GPLv3 text, the complete Corresponding Source of both (the pinned Yosys source with `abc` and `cxxopts`, the Fedora source packages of the two DLLs, the YosysHQ build recipe) in the source package beside the archive, and the DLLs stay separate, replaceable files. The Toolchain 1.0 DE10-Lite notices called termcap "MIT-style"; that was wrong and is corrected.

## 3. The other open items of the macOS review, for Windows

* **L1/L2** closed by removal (section 1). **L8** closed by removal.
* **L4** Yosys provenance: the Windows binary is the unmodified YosysHQ release file at the same pinned commit; the recipe that explains `-dirty`, the source and the licence texts of the libraries compiled into Yosys are in the packages. The macOS rebuild evidence concerns the macOS binary; **no Windows rebuild was made and a bit-identical rebuild is not claimed.**
* **L5/L10/L11** (libusb text, openFPGALoader bitstreams, Lima) are macOS-only or covered by section 1.
* **L6** GHDL runtime origin: the official `ghdl-mcode-6.0.0-ucrt64.zip`, built by GHDL's CI on MSYS2 UCRT64 with GNAT 15.2.0 (the GCC Runtime Library Exception covers libgnat and libgcc_s; libwinpthread is MIT and BSD-3-Clause; zlib1 is Zlib).
* **L9** replacement rights: with the Phase 5D behaviour implemented for Windows in Phase 5H (`tests/windows-install/modified.test.ts`) a changed but complete toolchain is "installed but modified" and fully usable; nothing is restored unless the student chooses Repair; missing or broken files stay a repair case; installer and download verification are unchanged. The Windows notices say so and do not mention Apple code signing.
* **Source delivery**: one corresponding-source package beside each binary archive (`MIX-FPGA-Nexys-A7-Support-1.1-Windows-x64-Sources.zip`, `MIX-FPGA-DE10-Lite-Support-1.1-Windows-x64-Sources.zip`); no written offer.
* **Not redistributed and never installed by MIX-FPGA**: Altera Quartus Prime Lite and the MAX 10 package (the student supplies the files and accepts Altera's licence), Altera's USB-Blaster driver, Digilent Adept Runtime and Utilities (proprietary; the student installs them from Digilent), Zadig/libwdi (the Apio `drivers` package is an empty placeholder).

## 4. Not claimed

No legal clearance is claimed. If a licence owner or an adviser disagrees with a conclusion above, the corresponding treatment (for example removing the unused Readline-linked `vvp.exe`) is a normal engineering change in a later toolchain version.
